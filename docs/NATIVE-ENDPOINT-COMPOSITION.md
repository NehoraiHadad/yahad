# Native endpoint and installed-role composition

This is a code-only development checkpoint. The authority and owner executables
still reject production activation. No Windows endpoint, service, account,
installed ACL, real delegation, credential or listener has been created.
The selected future acceptance computer is **ASUSHADAD**. A VM is optional,
not a prerequisite. The normal-host proposal below supersedes older VM-only text.

## Connected code path

`InstalledAuthorityComposition` builds the actual intake selector, owner ledger,
request router, transaction writer and existing admitted-runtime health controller.
The private fixture uses the same construction, actual private files, real
SQLite/Store, actual child jobs and file-only control, with synthetic principals
and outer-host observations. It does not simulate a successful installed account.

`InstalledIntakeSelection` reads a protected available pointer and exact receipt,
binds receipt bytes to its digest and selected payload manifest, schema, version,
byte count and the existing immutable policy/pin anchor. It derives the complete
operation server-side from the actual installed epoch, selection and web origin.
The request carries only an opaque target fingerprint. Changed intake/head after
display prevents approval/commit. A receipt's protection is a boundary supplied
by the existing sole updater; this code does not invent release authenticity,
enroll a signing key, publish a receipt from a browser or validate an unsigned
developer archive as a trusted release. The real updater-to-protected-intake
publisher remains necessary before enabling this path.

`AuthorityEndpointRouter` connects bounded request/status/confirmation frames to
that selector and ledger. Role and principal come from the connection adapter,
never JSON. It persists intent before work, rejects changed request-ID replays,
and refuses to infer completion from an unfinished record after restart. A single
native approval authorizes an exact operation. One separately bounded delegation
can authorize routine automatic updates; policy/pins, data/key, origin, schema,
version bounds, expiry and operation budget still constrain every update.
Mode publication uses a flushed temporary file and write-through rename; a crash
residue blocks mode interpretation pending reconciliation. Cancellation or a lost
reply is not success. Uncertain commit/probe/runtime ownership remains retained
and recovery-required; explicit observed cleanup does not itself reconcile an
interrupted durable transaction.

`InstalledStateFiles` connects the writer, ledger, resolver, recovery admission
and Store lease handoff to exact file roles. Private constructors retain actual
private-file checks. Installed constructors validate actual native owners/DACLs,
fixed service identities, no-follow/single-link handles and immutable installation
anchor. Files created by installed code receive scoped roles at creation; no
permission repair of an existing file is implemented or exercised. Probe execution
uses the fixed installer-owned, hash-bound Node runtime instead of app-owned code.
Real installed access is still unaccepted; synthetic role callbacks cannot prove
Windows access checks.

`WindowsAuthorityEndpoint` contains the real compiled local-only first-instance
pipe creation and client operations. The exact owner/runtime client gets individual
read/write/synchronize rights, excluding pipe-instance creation. Identification
occurs after a bounded message read and reverts synchronously before file work or
await. Owner client checks exact SCM account/config/PID, retains a process handle,
checks its image and service token and refuses exit/change before accepting a
reply. Cross-account process/token query access is an explicit acceptance item;
there is no fallback to PID-only authentication or new privileges. Current Program
never invokes these methods. In-memory transport tests do not exercise native
pipe identification, remote rejection, service tokens or cross-account ACLs.

`Yahad.Owner` compiles a UTF-8 Hebrew RTL WPF confirmation window and a concrete
fixed transport factory. Its shared state model binds installation, challenge,
digest and expiry, accepts one answer, and never resends an uncertain answer.
The window distinguishes exact updates from bounded delegation. Its current App
entry exits without opening a window or connection. Compilation is not visual QA;
no screenshot or successful native confirmation is claimed. Existing family and
WhatsApp setup remain in the web app.

## Remaining code, separate from acceptance permission

Do not treat the disabled executables as an installable family product. The next
production wiring must connect the authority SCM entry and runtime waiting-host
handshake to retained cross-service handles/outer job and concrete old-generation
quiescence. The installed composition currently requires those existing lifecycle
adapters as trusted constructor arguments. Never substitute a local authority-SID
child for the runtime service or fabricate an empty old-generation job.

Also required: the existing sole updater's protected intake publisher, native
runtime request/status transport wired into the existing server injection seam,
bootstrap provisioning/repair/uninstall executor with durable receipts and correct
unelevated-owner capture, and a frozen combined installer/dependency closure.
Authority/owner activation must stay denied until those are complete. Interrupted
routed requests are conservatively blocked; an owner-authenticated reopen/resume
workflow must bind the persisted operation before offering recovery in the UI.
These are code gaps, not an excuse to request broad host approval early.

## ASUSHADAD installation/check/uninstall proposal

The machine selection is authorized; the changes below are **not** authorized.
`installer/windows/asus-host-acceptance.json` is the single current proposal.
Only after the remaining code and exact package/hash inventory are populated and
reviewed should one action-specific request name that manifest and artifact.

1. Repeat exact collision checks immediately before execution. Abort if either
   acceptance service or either target tree already exists. Never adopt/reset an
   existing family installation or modify unrelated service/runtime/port settings.
   Read-only observation at this checkpoint found the two service names and two
   target directories absent; this is not a reservation of their future state.
2. Elevate once for installation of the verified package, not for every update.
   Create only `Yahad.Acceptance.Authority` and `Yahad.Acceptance`, separate
   passwordless virtual service identities with only SeChangeNotifyPrivilege,
   initially demand-start. No boot autostart or restart policy in this first check.
   Any later before-login/autostart/reboot test needs a specifically amended plan.
3. Install bootstrap/owner/probe and their private runtime closure under
   `C:\Program Files\Yahad.Acceptance`; create only new acceptance state under
   `C:\ProgramData\Yahad.Acceptance`. Apply closed per-role ACLs only in those new
   trees and exact service objects. Owner receives only companion execution and
   the documented read-only authority identity checks; no state writes. Real
   process/token access must work narrowly or fail closed, not add broad privilege.
4. Test native account/role/pipe isolation and exact-operation confirmation using
   synthetic data first. Check actual runtime/outer-job assignment before Node
   resumes, continuous Store lease, failed start/stop, interrupted update and
   retained recovery ownership. Do not deliberately power-cut this working PC;
   use bounded controlled process failure. Keep unrelated applications running.
5. A separate web-handoff phase must name exact local ports/configuration. Existing
   account/WhatsApp onboarding is reused. No firewall rule, CA trust change,
   router forwarding, tunnel, DNS enrollment or public exposure is included in the
   service-only proposal. LAN/HTTPS acceptance requires its own concrete selected
   provider/configuration and narrow approval; do not claim server health proves
   tablet reachability or automatic tablet certificate trust.
6. Stop only the two owned services and observe full tree exit. Remove their exact
   SCM registrations and installer-owned binary tree using verified install receipt
   identities. Preserve `ProgramData` data, keys, policy/pins, backups and recovery
   journals by default, protected under the receipt's existing role controls.
   Report any Windows-owned service/profile/event residue; never delete shared
   profiles, event logs, global runtimes or other services. Permanent data removal
   is a separate explicit owner action. A normal uninstall is not byte-for-byte
   OS rollback and does not promise to remove SCM audit history.

No VM, snapshot, second computer, new Windows user or paid service is required by
this proposal. Optional backup/snapshot reduces risk but does not replace exact
permissions, preservation or artifact checks. ASUSHADAD already has developer
runtimes; empty-PATH tests here do not prove clean-machine installation with none
installed. Windows x64 is the proposed target; ARM64/all Linux distributions are
not implied.

API decisions follow Microsoft's [pipe access rights](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights),
[CreateNamedPipe contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea)
and [identification/reversion contract](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-impersonatenamedpipeclient).
